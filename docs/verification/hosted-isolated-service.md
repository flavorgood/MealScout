# MealScout hosted isolated verification

`render.isolated-verification.yaml` is a separate Blueprint candidate for a disposable web service. It is not the production `render.yaml` and is not connected to Render merely by existing in this repository. The production Blueprint and service stay untouched. The candidate fixes its source branch and turns service commit auto-deploys off; verify its actual commit before a manual deployment. A Blueprint has separate Auto Sync behavior: when connecting this file through the custom Blueprint Path, set **Auto Sync to No** in that Blueprint's Settings and review the first creation and every later Manual Sync before migrations or startup. Service `autoDeployTrigger: "off"` does not disable Blueprint Auto Sync.

The draft pins `region: virginia` as a **proposal**. The existing MealScout Render service was observed in Virginia through Render service metadata on 2026-09-28; without this field, Render's Blueprint default is Oregon. A same-region candidate would use a new Neon project in AWS `us-east-1` (N. Virginia). The lowercase `virginia` value is a [documented Render Blueprint region](https://render.com/docs/blueprint-spec). This source edit creates no service, selects no live target, and incurs no charge. Region cannot be changed on an existing Render service; review the proposed region before creation.

The recommended database target is a **new, non-cloned Neon project dedicated to MealScout** in the connected organization, on its root branch in AWS `us-east-1`, with a new database such as `mealscout_isolated_20260928`. The connected account's historical MealScout preview is in Ohio, has three archived branches and only `neondb` on each, and has no observed isolated database. Adding a new database there could give an empty database name, but would retain the old project's compute, access, region, and uncertain data provenance. Do not use that preview or branch from any existing customer/production branch for this candidate; [Neon child branches inherit parent schema and data](https://neon.com/docs/get-started-with-neon/workflow-primer). Before migration, record the new project's root lineage and verify zero application tables in the named database (therefore no customer rows). After migration, verify the expected schema and zero customer rows using counts only, without reading customer records. The URL/name guard is not evidence of these conditions.

Cost proposal for owner review: the Blueprint's `starter` web-service plan corresponds to 0.5 CPU / 512 MB and is listed at [about $7 per month](https://render.com/pricing) for a full month. The connected Neon organization's Launch plan picker showed Postgres at $0.106 per CU-hour and $0.35 per GB-month of storage on 2026-09-28, matching [Neon's published rate update](https://neon.com/blog/major-compute-price-reduction-on-neon). Propose one fixed 0.25 CU compute with five-minute scale to zero. At that observed rate, 10 active hours at 0.25 CU would add about $0.27 compute, while 730 active hours would add about $19.35; combined with a full-month Starter service, the examples are about $7.27 and $26.35 before storage, restore history, transfer, taxes, or later rate changes. An always-open application connection could prevent scale to zero. The new project's actual usage is unknown, so these are estimates, not a spending limit or permission to create resources. Recheck the displayed account terms and review the concrete cost/region with the owner before Neon project creation or Render Blueprint connection.

Before connecting it, provision a new empty Neon database named `mealscout_isolated_*` with no customer rows or production branch clone. Supply that database's URL only to this service's `DATABASE_URL`; the deploy migrator removes Neon `-pooler` for migrations. If a separate `MIGRATION_DATABASE_URL` is supplied later, it must point to the same host and database as the runtime URL. Supply `CLIENT_ORIGIN` and `OWNER_AI_PUBLIC_BASE_URL` as this service's own HTTPS origin, not the customer domain. Do not copy production env groups or Stripe/Brevo credentials. The Blueprint deliberately contains no provider keys or customer account credentials.

At service creation, review its name, branch, source commit, database target, environment variables, and plan before allowing the first build, pre-deploy migration, and start. The isolated flag suppresses startup jobs and admin bootstrap only on the dedicated Render service name; the live MealScout service ID also explicitly refuses that flag. Both the server and deploy migrator reject a database URL outside `mealscout_isolated_*`; hosted mode also requires a Neon host. These checks reduce accidental target selection but do not prove data provenance, account ownership, or provider safety. Request routes can still call providers when credentials are added.

First prove source identity, migration results, health, disabled host intake, and zero provider credentials against the disposable service. Then map a Stripe **test** merchant, a Brevo sender, and an owned test inbox to this service before a deliberately bounded provider-origin journey. Keep actual sends/payments and real customer accounts outside synthetic verification. A successful build or health response alone is not provider or customer acceptance.
