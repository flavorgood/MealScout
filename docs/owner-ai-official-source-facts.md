# Official public source facts in native owner drafts

The authenticated MCP tool `get_mealscout_official_source_facts` reads current public source links for the exact native business attachment. It returns a proposed packet or explicit holds. It performs no canonical write and creates no draft.

Supported extraction is deliberately bounded: explicit public menu links, telephone links, and social profile destinations. A Square published-page adapter parses the exact JSON bootstrap assignment, visits only visible current-page content, and accepts same-origin PDF blocks explicitly described as a menu. It does not execute scripts or use hidden template hours, contact defaults, store settings, filename dates, or guessed prices.

`packet.sourceFacts` preserves the complete current official URL set and each exact field/value, source URL, server capture time, 24-hour expiry, SHA-256, public-access classification, and qualification. Native create/update verifies the facts and replaces caller capture declarations with actual server observations. The stored packet, normalized evidence plan, and exact consent fingerprint include this evidence.

Approval re-fetches all current official sources, checks semantic values and conflicting facts, verifies menu-link reachability, and rejects unavailable cited sources or changed official URL sets. Dynamic HTML changes alone do not invalidate unchanged facts. The canonical transaction rechecks current owner, field visibility/quarantine, the full official URL set, expiry, expected native versions and unchanged draft content. OAuth/MCP approval also locks and rechecks the current credential after source fetching, including revocation, expiry and approval/context scopes.

The owner still must review and explicitly approve the exact native revision. Existing owner-session and connector authorizations remain required; source declarations grant no access. All five existing restaurant-backed native food types use this flow. Location, host, supplier and event adapters remain separate unsupported work.

Menu item contents, prices, stock/availability, dietary claims and effective dates are held for separate verification. Dated attendance, absolute year, timezone and public/private event facts are also held. This slice does not implement those extractors, schedule nightly canonical writes, create standing consent, or demonstrate a live customer write. Existing Central-midnight link checks and their historical unverified receipts are preserved.

Validation: actual native PGlite draft/consent/writer proof and adversarial source/visibility/race checks; existing owner-AI and source-check regressions; typecheck/build results are recorded in the adjacent task evidence. Synthetic fixture owners prove only local behavior. Sweet Love's fresh official page supplies its explicit menu PDF destination; no authenticated customer draft exists from that observation alone.

## Complete semantic section proposals

Version 2 evidence binds the complete normalized menus/schedules proposal values to official public structured content, its source/capture/hash, validity interval and exact revision. The bounded JSON-LD adapter accepts an embedded menu for the exact official business URL only when every offered item has an explicit current absolute validFrom/validThrough, exact USD price and InStock declaration. Conflicting values or validity dates, incomplete competing menus, unavailable sources and malformed/unsupported nested contexts hold complete sections. Source-backed menu upserts preserve omitted owner metadata and missing existing items; they do not infer removals. Existing item classification conflicts hold application.

A schedule proposal requires an explicit exact-URL business performer, scheduled physical event, consistently public audience and unrestricted venue, absolute year/offset dates plus explicit IANA timezone, exact minute representation and a future event. Mixed/private/invited audiences, restricted military venues, private weddings, cancelled events, timezone mismatch and DST-ambiguous local times are held. Full section values and menu effective-date intervals are rechecked before native exact-consent application.

The safe fetcher retains its default512KiB deadline/DNS/IP/TLS/redirect/login/size protections. Verified menu destinations use an opt-in16MiB bound; this allows the observed10,179,617-byte Sweet PDF without loosening nightly/default source checks. The PDF has no prices/effective date and remains an inspected-content hold. Parsing its metadata or filename does not supply either fact. Automated PDF item extraction and nonrestaurant native adapters remain unfinished. Nightly private semantic observations and native owner draft preparation are described below; automatic canonical application has no standing consent.

## Native source review and automatic proposals

The existing scheduler also captures private semantic proposals at America/Chicago midnight for active public native food profiles, paging the existing table. A separate immutable per-profile/day telemetry receipt carries observations and explicit holds; it has no owner principal, creates no owner draft, and performs no canonical or social writes. Concurrent/repeated runs are deduplicated; historical source-check receipts are unchanged.

Current actual owners can read visible, still-current source reviews in AI Control and prepare a fresh official-source draft without copying JSON or granting a new connector. The strict owner-session source-draft endpoint accepts no supplied facts, identities or consent, re-fetches sources and preserves native versions. Native draft insertion locks current source authority and rechecks versions; exact-revision approval remains the canonical write boundary. Removed/hidden links, disabled/transferred owners and expired evidence are withheld. Unsupported/undated PDF content remains held. This does not create standing approval or prove any live customer draft/application.

## Type-specific native food adapters

Current owner/session or existing scoped connector authority binds restaurant_native, truck_native, bar_native, caterer_native or private_chef_native. The native type and owner ID are included in the expected version fingerprint, current snapshot, normalized plan and exact MCP consent. A type/owner change holds application even without a timestamp change. Legacy isFoodTruck identity follows the native public profile resolver.

Profiles and menus retain their existing native stores. Trucks retain dated movement in truck_manual_schedules. Fixed and service food profiles store dated appearances in food_business_appearances, scoped to current owner and exact profile type. Migration144 is additive; it converts no historical rows and creates no host, booking, payment or pickup authority. The existing public event view reads these appearances with current publication policy, public access, expiry, source section integrity, exact current official source set and interval checks. Private events/addresses and corrupt/stale/source-removed observations stay withheld. Public venue appearances do not expose a private chef's static address.

Nightly source reviews remain private proposals: they never create an owner grant/draft/consent or apply content. Actual pilot changes need verified facts, an actual authenticated native draft and exact current owner approval. Location, host and supplier adapters remain separate unfinished work.

Deployment changes the native profile version fingerprint to include current owner and adapter type. Pending drafts using the old fingerprint must refresh their native context and obtain consent for a fresh exact revision; old consent is never broadened. The four first-candidate defects (current address visibility, nontruck closure overlap, historical limit exhaustion and stale public type) were independently reproduced and repaired before release.
