# Official public source facts in native owner drafts

The authenticated MCP tool `get_mealscout_official_source_facts` reads current public source links for the exact native business attachment. It returns a proposed packet or explicit holds. It performs no canonical write and creates no draft.

Supported extraction is deliberately bounded: explicit public menu links, telephone links, and social profile destinations. A Square published-page adapter parses the exact JSON bootstrap assignment, visits only visible current-page content, and accepts same-origin PDF blocks explicitly described as a menu. It does not execute scripts or use hidden template hours, contact defaults, store settings, filename dates, or guessed prices.

`packet.sourceFacts` preserves the complete current official URL set and each exact field/value, source URL, server capture time, 24-hour expiry, SHA-256, public-access classification, and qualification. Native create/update verifies the facts and replaces caller capture declarations with actual server observations. The stored packet, normalized evidence plan, and exact consent fingerprint include this evidence.

Approval re-fetches all current official sources, checks semantic values and conflicting facts, verifies menu-link reachability, and rejects unavailable cited sources or changed official URL sets. Dynamic HTML changes alone do not invalidate unchanged facts. The canonical transaction rechecks current owner, field visibility/quarantine, the full official URL set, expiry, expected native versions and unchanged draft content. OAuth/MCP approval also locks and rechecks the current credential after source fetching, including revocation, expiry and approval/context scopes.

The owner still must review and explicitly approve the exact native revision. Existing owner-session and connector authorizations remain required; source declarations grant no access. All five existing restaurant-backed native food types use this flow. Location, host, supplier and event adapters remain separate unsupported work.

Menu item contents, prices, stock/availability, dietary claims and effective dates are held for separate verification. Dated attendance, absolute year, timezone and public/private event facts are also held. This slice does not implement those extractors, schedule nightly canonical writes, create standing consent, or demonstrate a live customer write. Existing Central-midnight link checks and their historical unverified receipts are preserved.

Validation: actual native PGlite draft/consent/writer proof and adversarial source/visibility/race checks; existing owner-AI and source-check regressions; typecheck/build results are recorded in the adjacent task evidence. Synthetic fixture owners prove only local behavior. Sweet Love's fresh official page supplies its explicit menu PDF destination; no authenticated customer draft exists from that observation alone.

## Complete semantic section proposals

Version 2 evidence binds the complete normalized menus/schedules proposal values to official public structured content, its source/capture/hash, validity interval and exact revision. The bounded JSON-LD adapter accepts an embedded menu for the exact official business URL only when every offered item has an explicit current absolute validFrom/validThrough, exact USD price and InStock declaration. Conflicting values or validity dates, incomplete competing menus, unavailable sources and malformed/unsupported nested contexts hold complete sections. Source-backed menu upserts preserve omitted owner metadata and missing existing items; they do not infer removals. Existing item classification conflicts hold application.

A schedule proposal requires an explicit exact-URL business performer, scheduled physical event, consistently public audience and unrestricted venue, absolute year/offset dates plus explicit IANA timezone, exact minute representation and a future event. Mixed/private/invited audiences, restricted military venues, private weddings, cancelled events, timezone mismatch and DST-ambiguous local times are held. Full section values and menu effective-date intervals are rechecked before native exact-consent application.

The safe fetcher retains its default512KiB deadline/DNS/IP/TLS/redirect/login/size protections. Verified menu destinations use an opt-in16MiB bound; this allows the observed10,179,617-byte Sweet PDF without loosening nightly/default source checks. The PDF has no prices/effective date and remains an inspected-content hold. Parsing its metadata or filename does not supply either fact. Automated PDF item extraction remains unfinished. Native nonfood content adapters are described below. Nightly private semantic observations and native owner draft preparation are described below; automatic canonical application has no standing consent.

## Native host/location and supplier public content

Host and location are aliases of the same hosts row, not independent booking permissions. Current actual host owners can draft public name, phone, website, social links, logo and cover image. Current active supplier owners can draft public name, phone, website and logo. Migration145 adds only the nullable native public link/branding fields already consumed by the existing public projectors plus a separate owner_ai_native_profile_drafts store. Addresses/coordinates, host capacity, availability, events, reservations, parking-pass prices, supplier product ordering, payments and delivery controls are excluded from this adapter. Supplier descriptions remain derived from existing operational notes and are not editable through it.

The existing AI Control page offers a reachable native content card, with links from host and supplier dashboards. Empty-body source-draft requests capture current owner-configured official public URLs with the existing SSRF-safe fetcher. Only supported explicit public contact/social facts become proposals; missing, unavailable, conflicting and unsupported facts stay held. Source menu/schedule fields cannot be coerced into host booking or supplier purchasing authority. The existing Central-midnight scheduler pages hosts and suppliers once each, storing private checksum-bound observations without credentials, native drafts, owner consent or canonical writes. Historical food source-review receipts are kept separate.

Native drafts are new immutable IDs (revision1); refreshing creates a new draft. A hash binds target kind/ID, current owner, actual native row version, public content snapshot, packet including exact provenance, immutable image byte manifest and expiry. Owner-session approval supplies that exact revision/hash, recaptures official-source meaning, repeats current authority under native/owner/draft locks, and records consent atomically with the native update. Transfer, disabled owner, hidden/removed links, stale row context, expired evidence, changed source meaning and tampered packets hold application. Remote images reuse the existing bounded safe raster capture, byte/hash checks, private authenticated preview and existing image hosting configuration; the rights affirmation is shown before consent. Existing restaurant-scoped connector credentials are not broadened to these stores.

The startup and nightly read-only reason aggregate counts only existing integrity-checked, exact-day private food source-review receipts, emitting no customer identifiers, source URLs or values. Reasons are exclusive; source-ready observations count separately as requiring owner consent. Failures that left no historical receipt remain unclassified rather than being inferred from a completion total. This does not prove any live customer draft or approval and does not create standing consent.

## Aggregate reason coverage for future review runs

Each completed food or native-content review invocation records a separate checksum-bound system telemetry summary with fixed outcome/reason counters, a random run ID, lane/day and run times. It contains no owner/profile IDs, source URLs, proposed values, body data or exception text. Early current-owner/adapter, public-policy, changing-authority and receipt-integrity failures now receive fixed reason categories even when they cannot create a per-profile observation. Unknown exceptions retain an explicit unknown-cause category. The workflow's existing reads, native ownership checks, captures and per-profile observations remain scoped as before; run summaries create no customer draft, consent or canonical update.

heldOutcomesRecorded counts observed holds; heldWithReason/classifiedHeld counts known causes; heldWithoutReason/unclassifiedHeld counts unknown causes. Source-ready observations requiring owner consent remain separate from holds. Failed summary persistence returns persisted:false with safe in-memory counts and cannot claim durable coverage. Startup reads only the latest valid summary per lane from this exact telemetry event, verifying strict schema, checksum and count identities. Retries and concurrent runs retain distinct run summaries; their counts are not summed into a fabricated daily census. Invalid scanned receipts are reported as such. Enumeration or whole-run failures cannot claim a completed run.

Scheduler startup and completion emit single JSON lines containing only these safe aggregates. Future run coverage does not rewrite historical per-profile receipts or supply missing historical reasons: the October 1 run's 840 holds without persisted reason receipts remain unclassified. The dominant historical cause remains unknown. New run execution and production coverage must be reported from actual receipts, separately from disposable fixture proof.
