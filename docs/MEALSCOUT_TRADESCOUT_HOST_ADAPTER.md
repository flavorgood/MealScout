# MealScout consumer boundary for the TradeScout hosting hub

Thomas's current direction is that TradeScout profiles form the hosting hub alongside tools, while MealScout retains its food product and permissions. Shared profile/domain/hosting primitives belong to the TradeScout owner. This consumer slice aligns the existing SDK/API transport and supplies a handler to the existing native HTTP runtime; it creates no parallel hosting backend, database, DNS policy or public redirect.

## Implemented consumer repair

MealScout already exports the full `MealScoutApp` through `vite.lib.config.ts`. Its `performMealScoutSSO` helper now uses the same `apiUrl` resolver as the embedded application's native API requests when its optional `baseUrl` is omitted. For an embedding TradeScout page, the old default incorrectly posted to the embedding origin's `/api/auth/tradescout/sso` even when the application's API resolver selected the MealScout API. Explicit SDK base overrides, including an explicit empty same-origin override, retain their existing behavior.

TradeScout API/auth context recognition now requires `thetradescout.com` or its actual subdomains. A hostname merely containing `tradescout`, such as `evil-tradescout.example`, no longer receives the MealScout fallback or TradeScout OAuth app context. This origin recognition chooses transport; it grants no role, restaurant ownership, publication or payment authority. Native MealScout and isolated deployment API/session behavior remains covered by focused source-only regressions.

The SDK context's `user`, `location` and `scoutBridge` are not proof of native authentication or profile ownership. MealScout still reads its server-owned session and business permissions. The current receiver at `server/unifiedAuth.ts` and existing SSO identity-hardening work require their own coordinated acceptance; this consumer repair changes neither JWT verification nor identity linking or role mapping.

## Interface coordination required from the hosting owner

The shared registration contract is now pinned below. A live registration still needs verified existing identities and native configuration for these boundaries:

- Actual TradeScout profile/tenant binding and the MealScout source restaurant/profile ID; an opaque public-link tenant is not an authenticated account mapping.
- The mounted full-app route and native public profile mapping, including deep links, assets and native food/order/checkout/workspace journeys.
- The MealScout API/proxy base and session/CSRF/auth handoff contract, with issuer/audience/identity boundaries, cookie isolation and supported origins. No browser token or unreviewed SDK context may confer native owner access.
- Custom-domain host admission, TLS and canonical/SEO ownership, including conflict, revocation, owner transfer and disabled/hidden/quarantined profiles. A DNS match alone does not authorize a hosting tenant or an application session.
- The online-presence scoring input/version contract, with server-owned subject, source evidence, freshness and permitted public projection. Existing MealScout completion status and client-reported quality events are separate evidence kinds and must not be silently reinterpreted as a shared hosting score.

`docs/ECOSYSTEM_PUBLIC_LINKS.md` and migration143 currently authorize only source-owned optional `public_link_only` sharing. That approval does not authorize full hosted profile data, cross-product account permissions or contact/order/payment access. It must retain its generation/revision/digest/expiry and revocation guards. Native public admission/projection, canonical food-type routes and custom-domain current-owner checks remain source-owned.

## Native upgrade consumer for v2

The native server still uses `/socket.io/`, Engine.IO4, both polling and WebSocket transports, truck location events and kitchen subscriptions. `server/index.ts` now passes the same native HTTP session middleware into `setupWebSocketServer`. This uses HTTP's actual `tradescout.sid` cookie, secret, domain and PgSession store. Engine.IO middleware resolves the actual session and native user before initial polling or WebSocket101, rejects unavailable/disabled authenticated users, and checks an existing engine sid against its original native actor, session, public Host and Origin. Native anonymous public discovery remains allowed; native restaurant/kitchen ownership checks and public projections remain in their original handlers. SDK auth/role hints grant no account or room access. Engine close removes only its authority record; Socket.IO disconnect retains native room cleanup.

Upgrade support is opt-in with `nativeRealtimeAuthorization: "mealscout-engine-session-v1"` in `createMealScoutHostedRuntimeBinding`. Supply it only when the fixed existing upstream is confirmed to run this exact reviewed native pre101 repair; it is an operator attestation, not a runtime version or authentication proof. Omitting it preserves the five-field HTTP binding. With it, the immutable optional capability declares `paths: ["/socket.io"]`; its handler accepts only the actual `/socket.io/` route and valid Engine.IO4 WebSocket query. HTTP polling continues through the same full native HTTP handler and upstream. No native listener, session store, worker or registration is created by the factory.

The relay retains the original request URL, native cookie/authorization, first-party HTTPS Origin, protocol key, client head bytes and raw frames. It replaces caller forwarding claims with the bound public Host/HTTPS and immediate peer, and connects only to the fixed native origin with that origin's TLS authority. It waits for the repaired native runtime's validated101 before calling `context.accept(close)`, checks the exact WebSocket accept key, and releases client101/head/frames only on true. All setup work is returned as a Promise. Gateway abort, refused/late claim, setup timeout, disconnect or transport error invokes idempotent teardown of the selected upstream/client sockets. No platform principal or native owner is inferred from host registration.

The v2 gateway retains its fixed capacity,5s claim deadline,4096 incoming-head bytes,32MiB incoming lease ceiling,256KiB queued writes sampled every250ms,30s authority checks and15min maximum lease. The relay also checks the native socket's outgoing queue at the same256KiB/250ms bounds, limits native handshake headers to16KiB and native handshake head to64KiB, and streams with backpressure. A lease ending closes this native engine transport and its rooms; the existing native client must reconnect and establish/revalidate its actual session. This lifecycle is source-prepared and awaits real allocated runtime acceptance.

The server owner must reserve/register the approved host on the exclusive shared HTTP-server facade before traffic. An Express handler or prepended asynchronous upgrade listener alone does not isolate platform Engine.IO listeners. Unknown/canonical Trade hosts keep the shared contract's original routing; pending/disposed reservations remain closed. The HTTP handler still returns426 for upgrade headers incorrectly delivered through HTTP routing.

`useFoodTruckSocket` now keeps one reconnecting native socket and retains the latest nearby subscription and desired restaurant subscriptions across transient disconnects. Every new native connection resends those intents. Explicit disconnect removes only its manager listeners and socket; a frontend account change clears private subscription intent and establishes a fresh transport, whose authority still comes from native cookies. The hook handles both native private `location_update` and public `truck_location_update` events and uses current callbacks. It sends no client auth/role grant. The kitchen client already resubscribes and refreshes canonical queries on connect. These client changes are source-reviewed only until actual reconnect and room acceptance runs.

Both native middleware and relay compare the literal raw pathname as well as its parsed form, so traversal/encoded/descendant aliases cannot substitute for the actual protocol route. HTTP polling and upgrades explicitly use the fixed native origin as TLS authority while retaining the bound public HTTP Host.
